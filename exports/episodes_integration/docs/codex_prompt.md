# Промпт для Codex — внедрить авторазметку эпизодов (суточный пересчёт + кэш)

## Контекст
В каталоге `episodes_integration/` лежит готовый самодостаточный пакет авторазметки:
- `episode_rules_v10_1.py` — алгоритм. Интерфейс `run_all(tele_df, vsp_df, wells=None) -> DataFrame`. **Не менять.**
- `compute_episodes.py` — **готовый CLI батч-раннер** (точка входа суточного пересчёта):
  загружает телеметрию + прогноз обводнённости, подмешивает `wct_pred`, парсит VSP,
  прогоняет `run_all` по всем скважинам, **атомарно** пишет результат, проставляет
  `computed_at` и `model_version`, устойчив к падению по одной скважине.
- `docs/input_schema.md`, `docs/output_schema.md` — схемы входа/выхода.
- `requirements.txt` — pandas, numpy, pyarrow.

Запуск раннера:
```bash
python compute_episodes.py --telem <telem.csv> --wct <wct.csv> --out <episodes.parquet> --model-version episode_rules_v10_1
```
Выход — таблица эпизодов со столбцами (см. `docs/output_schema.md`), включая готовую
колонку `explanation` (объяснение в 1 предложение для показа по клику).

## ГЛАВНОЕ ТРЕБОВАНИЕ — производительность
Приложение должно «летать»: **никакого вызова `run_all`/`compute_episodes` на HTTP-запрос.**
Расчёт — офлайн, по расписанию (по умолчанию **раз в сутки**, час из конфига). API/UI читают
только готовую таблицу `episodes`. Чтение эпизодов одной скважины — миллисекунды.

## Задача (обвязка вокруг готового раннера — логику НЕ писать заново)
1. **Планировщик**: запускать `compute_episodes.py` раз в сутки (cron / Airflow / системный
   таймер — по стеку проекта). Час и пути — в конфиге. Плюс CLI-команда для ручного запуска.
2. **Хранилище** `episodes` (таблица БД или parquet+индекс), схема — `docs/output_schema.md`,
   индекс `(well_id, start)`. Загрузку выхода раннера в хранилище сделать **атомарной**
   (staging → swap), чтобы UI не видел промежуточное состояние. (Раннер уже пишет файл
   атомарно; при заливке в БД повторить тот же принцип через транзакцию/перелив таблицы.)
3. **API**:
   - `GET /wells/{well_id}/episodes?from=&to=&label=&tier=` — чтение из `episodes`, без расчёта.
   - `GET /episodes/last_computed` — отдаёт `computed_at` (UI показывает «данные на …»).
4. **UI**: по клику на классификатор показывать поле `explanation` (готово, считать не нужно).
   Легенду/цвета категорий строить динамически из данных (набор категорий может расширяться).
5. **Конфиг**: пути к `--telem` и `--wct`, cron-расписание, `model_version`, путь/коннекшн хранилища.
6. **Логи/мониторинг**: число скважин и эпизодов, длительность прогона, список упавших скважин,
   `computed_at` последнего успешного пересчёта.

## Ограничения
- `episode_rules_v10_1.py` импортировать как есть, **не трогать детекторы**.
- Зависимости из `requirements.txt`, версии не понижать.
- Время хранить в UTC; форматирование — на стороне UI.
- Прогноз обводнённости (`full_inference_water_cut.csv`) — вход от отдельной модели; если его
  нет, категории «Рост/Снижение обводнённости» будут пустыми (это ожидаемо).

## Критерии приёмки
- В пути обработки запроса эпизодов нет вызова `run_all`/`compute_episodes` (только чтение БД/файла).
- Суточный пересчёт — один планируемый джоб, атомарно обновляющий `episodes`.
- `explanation` есть у каждого эпизода и показывается в UI по клику.
- Падение по одной скважине не теряет остальные; ошибка залогирована.
- Описано: как запустить пересчёт вручную и как настроить расписание.


## Формат выгрузки приложения и слоты auto_*
Свежая выгрузка (well_graph_data_<well>_2026-06-21*.csv) — супер-набор: алгоритм работает с ней
как есть. В ней есть слоты для записи авторазметки:
- auto_episode_* (id/labels/start/end/confidences) = таблица episodes (поэпизодно).
- auto_target_* = построчные дневные флаги (зеркало ручных target_*). Заполняются командой
  compute_episodes.py с опцией --enrich <out> (маппинг метка->колонка в docs/output_schema.md).

Для чарта Авторазметка (построчные дорожки) используйте auto_target_* из --enrich или стройте
их на фронте из таблицы episodes по перекрытию интервалов — на ваш выбор по производительности.


## Расчётный Кпрод на графике
Для линии «Кпрод_алгоритм» используйте суточный ряд расчётного Кпрод: `compute_episodes.py --kprod <out>`
(файл well_id,date,kprod_calc — мёржить по (well_id,дата) как обводнённость) либо колонку `kprod_calc`
из `--enrich`. Выводить отдельной линией со своей осью.


## ФИКС: объяснения показываются как «-»
Причина: при заполнении слотов auto_episode_* (id/labels/start/end/confidences) НЕ пробрасывается
объяснение — отдельного слота под текст не было. Объяснение есть у каждого эпизода в колонке
explanation (выход compute_episodes / таблица episodes), но в построчные auto_episode_* оно не попадало.

Что сделать (любой из путей):
- A (правильный): тултип/панель эпизода берёт текст из episodes.explanation по ключу
  (well_id, label, start). Поле непустое для ВСЕХ эпизодов.
- B (если UI читает из построчной выгрузки auto_episode_*): использовать новый слот
  auto_episode_explanations — он формируется compute_episodes.py --enrich ПАРАЛЛЕЛЬНО
  auto_episode_labels (та же «|»-склейка и порядок), поэтому i-е объяснение соответствует
  i-й метке. Пробросить его в объект эпизода как explanation.

Проверка: в выгрузке --enrich колонка auto_episode_explanations непустая там же, где
auto_episode_labels; UI по клику показывает текст, а не «-».
